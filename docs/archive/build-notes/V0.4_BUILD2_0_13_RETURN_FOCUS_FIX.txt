CRITICAL FIX: Keyboard Focus Loss After Menu Close
	Problem:
		When navigating on the Dashboard with keyboard (Up/Down/Enter), then:
		1. Press Alt+M (Masters) or Alt+T (Entries) to open menu
		2. Press Esc to close menu
		3. Keyboard focus fell to document.body
		4. User had to click mouse once to regain keyboard navigation

		Root Cause:
			The menu controller in App.razor consumed the Escape event correctly,
			but when the menu closed, Blazor re-rendered and removed the previously
			focused menu items from DOM. The MainLayout's focus restoration logic
			used a generic page root fallback that didn't account for the specific
			Dashboard quick-access items that had been focused before the menu opened.
			This caused focus to slip to document.body instead of returning to the
			Dashboard.

	Solution:
		Implemented persistent focus tracking for Dashboard menu navigation:

		1. Added two new JavaScript functions in App.razor:
		   - window.texTrackRememberDashboardFocus()
			 Captures the ID of the currently focused Dashboard item before
			 opening a menu. Stores it in window.texTrackDashboardReturnFocusId.
			 Falls back to 'dashboard-page-root' if no item is currently focused.

		   - window.texTrackRestoreDashboardFocus()
			 Restores focus to the Dashboard item that was focused before the menu
			 opened. If that element no longer exists (e.g., if DOM was replaced),
			 falls back to 'dashboard-page-root'. Uses retry logic with RAF and
			 setTimeout to ensure focus succeeds after Blazor renders.

		2. Modified MainLayout.razor menu logic:
		   - ToggleMenu() now calls texTrackRememberDashboardFocus() before
			 opening a menu, capturing the current Dashboard focus target.
		   - Added pendingRestoreDashboardFocus boolean field to track when
			 focus restoration is queued.
		   - CloseMenu() now sets pendingRestoreDashboardFocus = true instead of
			 pendingPageFocus, triggering specific Dashboard focus restoration.
		   - OnAfterRenderAsync() now checks pendingRestoreDashboardFocus before
			 pendingPageFocus, ensuring Dashboard items are refocused with priority.
		   - Escape handler in HandleKeyDown() delegates to CloseMenu() which
			 handles the restoration.

	Files Changed:
		1. Components/App.razor
		   - Added texTrackRememberDashboardFocus() function
		   - Added texTrackRestoreDashboardFocus() function
		   - Window globals: window.texTrackDashboardReturnFocusId

		2. Components/Layout/MainLayout.razor
		   - Added pendingRestoreDashboardFocus boolean field
		   - Modified ToggleMenu() to call JS remember function
		   - Modified CloseMenu() to set restore flag
		   - Modified OnAfterRenderAsync() to handle restore flag
		   - Modified Escape handler in HandleKeyDown()
		   - Modified HandleLocationChanged() to clear restore flag

		3. No changes to Home.razor (Dashboard root already properly configured)

	Verification:
		Dashboard root element already has correct attributes:
			<section id="dashboard-page-root" ... class="dashboard ..."
					 tabindex="0" data-tt-page-root="true"
					 data-tt-page-autofocus="true">

TECHNICAL DETAILS
═══════════════════════════════════════════════════════════════════════════════

Escape Key Event Flow (Dashboard → Menu → Esc):
	1. User on Dashboard, quits quick-access item (focused on e.g., "dashboard-item-3")
	2. User presses Alt+M
	3. ToggleMenu(MastersMenuName) called
	4. ToggleMenu calls JS.InvokeVoidAsync("texTrackRememberDashboardFocus")
	   → window.texTrackDashboardReturnFocusId = "dashboard-item-3"
	5. Menu opens, openMenu = "masters"
	6. Menu renders, focus moves to first menu item "masters-item-0"
	7. User presses Esc
	8. Menu controller (App.razor line 255) captures Esc
	9. consume() prevents other handlers: preventDefault(), stopPropagation(), stopImmediatePropagation()
	10. Menu controller clicks overlay.click() to close menu (normal flow, not captured)
	11. CloseMenu() called from MainLayout:
		- openMenu = null (menu is removed from DOM)
		- openMasterGroup = null
		- currentMasterChildIndex = -1
		- pendingFocusId = null
		- pendingRestoreDashboardFocus = true ← NEW: marks focus restoration
	12. StateHasChanged() called
	13. Blazor re-renders, removes menu overlay from DOM
	14. OnAfterRenderAsync() fires after render completes
	15. Checks: if (pendingRestoreDashboardFocus) then:
		- pendingRestoreDashboardFocus = false
		- JS.InvokeVoidAsync("texTrackRestoreDashboardFocus")
	16. texTrackRestoreDashboardFocus() executed in browser:
		- Reads window.texTrackDashboardReturnFocusId = "dashboard-item-3"
		- Queries document.getElementById("dashboard-item-3")
		- If found, focus it with { preventScroll: true }
		- If not found (DOM was replaced), fall back to "dashboard-page-root"
		- Uses RAF + setTimeout retry loop (up to 40 attempts, 35ms each)
	17. Focus returns to dashboard-item-3
	18. document.activeElement === dashboard-item-3 ✓
	19. User can immediately press Down to navigate next item

Focus Restoration Fallback Chain:
	1. Return to previously focused Dashboard item ID (e.g., "dashboard-item-0")
	2. If that element no longer exists, try dashboard-page-root
	3. If dashboard-page-root still not found/not visible, retry with backoff
	4. Maximum 40 attempts over ~1.4 seconds (35ms between attempts)
