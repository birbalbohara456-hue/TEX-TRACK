PROBLEM:
	TexTrack Dashboard keyboard navigation breaks after closing a top menu
	(Alt+M or Alt+T) with Esc. Focus is lost to document.body, requiring
	a mouse click to restore keyboard functionality.

SOLUTION IMPLEMENTED:
	Added targeted focus tracking for Dashboard menu operations:
	1. Capture Dashboard focus ID before opening a menu
	2. Restore specific Dashboard item after closing menu with Esc
	3. Fallback to Dashboard root if original item is no longer in DOM

DETAILED ISSUE ANALYSIS
═══════════════════════════════════════════════════════════════════════════════

ROOT CAUSE:
	When a top menu closes, the focused menu item is removed from DOM by Blazor
	re-rendering. Browser automatically moves focus to document.body (default
	behavior when focused element is removed). The generic page-root fallback
	focus logic doesn't search Dashboard (it's outside the .workspace element),
	so focus remains on body, killing keyboard input.

IMPACT:
	- High: Breaks keyboard-first navigation on Dashboard
	- Frequency: 100% reproducible
	- Severity: Blocks keyboard workflow until mouse is used
	- User Impact: Forces users to mix keyboard+mouse navigation

SCOPE OF AFFECTED OPERATIONS:
	✓ Alt+M (Masters menu) → Esc
	✓ Alt+T (Entries menu) → Esc
	✗ NOT affected: Mouse-based menu dismissal
	✗ NOT affected: Other pages or voucher entry forms
	✗ NOT affected: Menu navigation while menu is open

ARCHITECTURAL DESIGN
═══════════════════════════════════════════════════════════════════════════════

DESIGN PRINCIPLES:
  1. Store only element IDs, not element references
	 → Prevents stale references after DOM replacements
	 → Survives Blazor re-renders

  2. Capture state at the moment it's needed
	 → Before menu opens, capture Dashboard focus
	 → Don't try to reconstruct state after-the-fact

  3. Fallback gracefully on missing references
	 → If original element doesn't exist, use page root
	 → If page root doesn't exist, retry with backoff

  4. Separate concerns by component
	 → MainLayout handles high-level focus flow
	 → JavaScript handles DOM-level focus operations
	 → Home.razor provides the stable structure

FOCUS RESTORATION HIERARCHY:
  Priority 1: Specific Dashboard item ID stored before opening menu
  Priority 2: Generic Dashboard page root (dashboard-page-root)
  Priority 3: texTrackFocusPageRoot() generic page root search
			 (only if not on Dashboard)

EVENT FLOW SEQUENCE:
  1. User on Dashboard with focus on item X
  2. User presses Alt+M/T
  3. ToggleMenu() invokes texTrackRememberDashboardFocus()
	 → window.texTrackDashboardReturnFocusId = X
  4. Menu opens, focus moves to menu
  5. User presses Esc
  6. Menu controller consumes Esc (preventDefault, stopPropagation)
  7. (Browser default: click overlay to close menu)
  8. CloseMenu() called
	 → pendingRestoreDashboardFocus = true
	 → StateHasChanged() queued
  9. Blazor re-renders (menu removed from DOM)
  10. Browser moves focus to body (focused element removed)
  11. OnAfterRenderAsync() fires after render
  12. Checks: pendingRestoreDashboardFocus === true
  13. Calls texTrackRestoreDashboardFocus()
  14. JS queries and focuses stored ID (or fallback)
  15. Focus restored to Dashboard
  16. Keyboard input works immediately
